Hybrid search is a smart call for this specific corpus — here's the reasoning:

Why hybrid fits the Ashen Era Archive specifically:
The archive is an invented fantasy world, so it's packed with made-up proper nouns — character names, faction names, artifact names, place names. Pure semantic (embedding) search is great at "meaning" but can blur on exact names, especially rare or unusual ones, since the embedding model has never seen these invented words before and may not represent them distinctly. Keyword search (exact/fuzzy term matching) catches "Ashvael" or "the Cindered Accord" precisely, even when the surrounding meaning is ambiguous. Combining both gives you the best of both: semantic catches paraphrased questions, keyword catches exact-entity lookups.

How this fits into the loop from Step 1:
Your "search" step (step 2 in the loop) now does two searches instead of one, then merges them:

Semantic search → ChromaDB, using the embedding (Voyage AI) → returns chunks by meaning.
Keyword search → a term-matching method (e.g. BM25) → returns chunks by exact word overlap.
Merge the two ranked lists into one combined ranking.

The merging part — a heads up on complexity:
ChromaDB doesn't do keyword/BM25 search natively — it's vector-only. So "hybrid" means running a separate keyword search (a simple library like rank_bm25, or ChromaDB's metadata where_document contains-filter as a lighter option) alongside your vector search, then combining the two ranked lists yourself. The standard simple way to merge two ranked lists fairly is called Reciprocal Rank Fusion (RRF) — it's a small formula, not a new system, so it won't eat much time.

This is exactly the kind of decision judges want to see explained in docs/decisions.md — "we chose hybrid search because invented proper nouns break pure semantic embeddings" is a strong, specific insight (not generic).

Why these particular chunks floated up (and it's normal):

Look closely — the ballad and the courtroom quote outranked the codex artifact plate, even though the codex explicitly mentions both "Cindered" and "Accord" and "Ashvael." That's BM25 behaving exactly as designed, for two reasons:

Term rarity (IDF): BM25 rewards words that are rare across your whole chunk set more than words that appear everywhere. If "Ashvael" and "Accord" both show up in many chunks (novel, wiki, codex, ballad), their rarity score drops, so a chunk doesn't get a huge boost just for containing them.
Document length normalization: BM25 slightly favors shorter chunks that pack the query terms densely, over longer chunks where the same terms are a smaller fraction of the total text. Your ballad chunk is short and dense with "Ashvael," so it scores competitively even without mentioning "Accord" explicitly.

This is not a bug — it's the actual tradeoff of pure keyword search, and it's a good, honest thing to note in docs/decisions.md: "BM25 alone sometimes under-ranks the most semantically central chunk when key terms are common across the corpus — this is a core reason we combine it with semantic search rather than relying on it alone." That's a real, specific insight judges want to see, not a hand-wave.

This also previews exactly why Step 5b matters: semantic search won't have this bias — it should recognize that the codex artifact chunk is conceptually the most relevant, even if BM25 under-ranks it by raw word statistics. Fusing both is what corrects this.

Step 5b: Semantic search (Voyage AI + ChromaDB)

The core idea: instead of matching exact words, you convert the query into a vector (a list of numbers capturing "meaning") using Voyage AI's embedding model, then ask ChromaDB to find chunks whose vectors are closest to it.

Key detail from the challenge doc, worth remembering: all Voyage voyage-4 series models share the same vector space. That means Person 1 can embed the full corpus with the stronger voyage-4-large model, while your search step embeds each incoming query with the cheaper, faster voyage-4-lite — no mismatch, no re-indexing needed. This saves your team API cost and time on every single search call, since queries are embedded far more often than documents.

Here's the wrapper:

python
import os
import voyageai
import chromadb

# --- one-time setup (do this once when your app starts) ---
voyage_client = voyageai.Client(api_key=os.environ["VOYAGE_API_KEY"])
chroma_client = chromadb.PersistentClient(path="./chroma_db")  # match Person 1's path
collection = chroma_client.get_collection("ashen_era_archive")  # match their collection name


def semantic_search(query: str, top_k: int = 10) -> list[dict]:
    """
    Embeds the query with voyage-4-lite, then asks ChromaDB for the
    closest matching chunks by vector similarity.
    """
    query_embedding = voyage_client.embed(
        texts=[query],
        model="voyage-4-lite",
        input_type="query",  # tells Voyage this is a search query, not a document
    ).embeddings[0]

    results = collection.query(
        query_embeddings=[query_embedding],
        n_results=top_k,
    )

    # ChromaDB returns parallel lists (ids, documents, distances) — zip them together
    output = []
    for chunk_id, text, distance in zip(
        results["ids"][0], results["documents"][0], results["distances"][0]
    ):
        output.append({
            "id": chunk_id,
            "text": text,
            "semantic_score": 1 - distance,  # convert distance to a similarity-like score
        })
    return output
